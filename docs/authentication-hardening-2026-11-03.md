# Authentication hardening — 3 November 2026

This release addresses the scoped JWT and OAuth assessments of the local application. Neither assessment demonstrated an authentication bypass or account takeover. The changes tighten the accepted token profile and remove two OAuth verification assumptions.

## Behavior

- Access JWTs must use HS256 and `typ:JWT`, carry an expiration, and have a valid signature, issuer, audience, and lifetime. Unsupported critical JOSE headers are rejected, including malformed or empty `crit` values. Existing tokens generated by the application retain their normal validity.
- GitHub sign-in always selects an email from `/user/emails` with `verified:true`, preferring the primary verified entry. A public profile email no longer skips that verification. Existing provider/user-ID matching and email-collision linking protections remain in force.
- GitHub repository authorization after App installation starts a fresh S256 flow, with a new state, verifier, and protected flow cookie tied to the initiating local account. Installation-triggered codes are not exchanged for credentials. Ordinary authorization sends the matching verifier, and the integration service rejects missing or invalid verifiers before contacting GitHub.
- Legacy pending repository flows without PKCE fail closed and can be restarted. The frontend popup and completion destination remain compatible.

No database migration, credential rotation, provider registration update, or frontend release is required. Deployment preserves production settings and data-protection keys. The GitHub App's existing installation callback must continue to reach the repository integration callback; the new authorization uses the existing configured callback URL.

## Validation

- 79 isolated authentication assertions passed using real authentication middleware, controllers, and application handlers with simulated provider HTTP responses and in-memory repositories. Coverage includes signed JWT algorithm/type/critical-header rejection, claim validation, state/correlation, cross-provider callbacks, PKCE code substitution, verified emails, account linking/unlinking, origin checks, fresh post-install authorization, and legacy/expired flow rejection.
- 45 existing security smoke assertions passed.
- GitHub HTTP/SQL smoke coverage passed against a disposable local SQL database, including successful post-install PKCE credential persistence, token protection, refresh, per-user repository access, and project links. The database was removed after the run.
- The API debug build passed with no warnings or errors. Production uses the existing self-contained Linux publish workflow.

Reproduce from the API repository:

```powershell
dotnet run --project tests/DevHub.AuthenticationSmoke/DevHub.AuthenticationSmoke.csproj --artifacts-path ../output/auth-hardening-validation
dotnet run --project tests/DevHub.SecuritySmoke/DevHub.SecuritySmoke.csproj --artifacts-path ../output/security-validation
dotnet run --project tests/DevHub.GitHubSmoke/DevHub.GitHubSmoke.csproj --artifacts-path ../output/github-validation
```

The GitHub SQL suite requires a local SQL Server and refuses a remote database. Real Google/GitHub accounts and consent flows are not exercised by these suites.
